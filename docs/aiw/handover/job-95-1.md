## 결정 사항과 이유

- **영상 파일 업로드 + 외부 링크 둘 다 지원.** 작업 지시는 "영상을 따로 업로드"지만, PHP `upload_max_filesize` 한도(로컬 2M, 운영 미확인)에 걸리면 긴 조리 영상은 아예 못 올린다. 링크 입력란을 함께 두어 한도와 무관하게 쓸 수 있게 했다. 둘 다 입력하면 매장 화면에 둘 다 표시된다.
- **컬럼명을 `video_link`로 했다.** `video_url`로 하면 모델 접근자 `getVideoUrlAttribute()`(업로드 파일의 asset URL)와 이름이 충돌한다. `image`/`image_url` 대칭을 유지하려고 컬럼은 `video`/`video_link`, 접근자는 `video_url`/`video_embed_url`로 나눴다.
- **업로드 한도를 하드코딩하지 않고 `RecipeMedia::maxUploadMb()`로 계산.** `upload_max_filesize`와 `post_max_size` 중 작은 값에서 1MB를 뺀다(제목·내용 등 다른 필드가 함께 전송되므로 한도에 딱 맞추면 거부됨). 검증 규칙(`max:`), 안내 문구, 클라이언트 사전 검사, API meta가 모두 이 값을 쓴다. 서버 설정을 바꾸면 코드 수정 없이 반영된다.
- **`.htaccess`에 `php_value upload_max_filesize`를 넣지 않았다.** 로컬 XAMPP(mod_php)에서는 먹히지만 운영 서버 구성이 불명확하고, `AllowOverride`가 허용하지 않으면 전체 사이트가 500으로 죽는다. 서버 설정 변경은 관리자에게 맡기기로 했다.
- **본사 작성 팝업과 수정 팝업을 하나의 폼으로 통합.** Quill 에디터 인스턴스를 2개 유지하면 초기화·동기화가 복잡해진다. Alpine `mode` 값으로 action URL(`:action`)과 `_method=PUT` 숨김 필드, 버튼 문구를 전환한다.
- **업로드 영상은 git에서 제외**(`/public/videos`). 대용량 바이너리가 저장소에 들어가면 안 되고, 운영 서버에 올라간 파일은 그 서버에 남아 있으면 된다. (참고: 기존 `public/images/recipes`는 추적 대상 그대로 두었다 — 기존 동작 변경을 피함.)
- **`docs/aiw/outbox`도 git에서 제외.** 사람에게 전달하는 일회성 산출물이다.
- **테스트는 `RefreshDatabase`를 쓰지 않는다.** `phpunit.xml`에 테스트 전용 DB 설정이 없어 개발 DB를 그대로 쓰기 때문에, 켜면 개발 데이터가 전부 날아간다. 대신 `tearDown()`에서 자기가 만든 레시피와 파일만 지운다.

## 주의사항·함정

- **테스트에서 HTTP 요청이 404가 난다.** 이 앱은 `APP_URL=http://localhost/leefriends`(하위 경로)로 서비스되는데 Laravel 테스트 클라이언트의 `prepareUrlForRequest()`가 `url($uri)`를 쓰기 때문에 요청 경로에 `/leefriends`가 붙어 라우트에 매칭되지 않는다. `HqRecipeVideoTest::setUp()`에서 `config(['app.url' => 'http://localhost'])` + `URL::forceRootUrl('http://localhost')`로 우회했고, 라우트명→경로 변환은 `path()` 헬퍼가 담당한다. 새 테스트를 쓸 때도 같은 처리가 필요하다.
- **포털 화면은 `?panel=1`을 붙여야 본문이 렌더된다.** 포털 레이아웃은 MDI 워크스페이스(탭 iframe) 셸이라, `panel` 파라미터가 없으면 껍데기만 나오고 `@section('content')`가 비어 있다. 테스트와 스크린샷 모두 `?panel=1`로 요청해야 한다.
- **Blade `@json`은 슬래시를 escape한다**(`http:\/\/...`). 카드 데이터는 `@click='open(@json($r))'`로 심기 때문에, 테스트에서 URL을 `assertSee()`로 찾으면 실패한다. 파일명(`basename`)이나 escape된 형태로 검증해야 한다.
- **로컬 `upload_max_filesize`는 2M이다.** 그래서 본사 폼에 «약 1MB 이하»로 표시된다. 버그가 아니라 서버 설정을 그대로 반영한 결과다. 로컬에서 큰 영상 업로드를 실제로 시험하려면 XAMPP php.ini를 고쳐야 하는데, 그 파일은 작업 디렉터리 밖이라 에이전트가 건드릴 수 없다.
- **헤드리스 Chrome 스크린샷은 `--user-data-dir`을 반드시 지정한다.** 지정하지 않으면 사용자의 기존 Chrome 프로필과 충돌해 프로세스가 영영 멈춘다(실제로 한 번 120초 타임아웃으로 백그라운드로 밀렸다). 경로는 `/c/Program Files (x86)/Google/Chrome/Application/chrome.exe`.
- **`php artisan test` 결과가 `DEPR`로 표시된다.** `config/database.php`의 `PDO::MYSQL_ATTR_SSL_CA` 상수 deprecation(PHP 8.5) 때문이며 기존부터 있던 것이다. 실패가 아니다.
- **Pint 주의.** `vendor/bin/pint`를 `app/Http/Controllers/Portal/Hq/RecipeController.php`에 돌리면 기존 줄인 `new \DOMDocument()`를 `new \DOMDocument`로 바꾼다. 불필요한 diff라 되돌려 두었으니 Pint 전체 실행 시 다시 확인할 것.
- `Recipe` 모델의 `video_embed_url` 정규식은 유튜브 ID를 `[A-Za-z0-9_-]{6,}`로 본다. 인식되지 않는 호스트는 링크를 그대로 iframe `src`로 쓴다.

## 다음 세션이 바로 실행할 첫 작업

사람의 답변(운영 서버 업로드 한도 3지선다)을 확인한다.

- **"그대로 두고 링크만 사용"이면**: 코드 변경 없음. 작업이 끝났다고 한 줄로 알리고 멈춘다(커밋·배포는 사람이 버튼으로 수행).
- **"200MB"/"50MB"로 올리라면**: 애플리케이션 코드는 그대로 두고(한도는 `RecipeMedia::maxUploadMb()`가 `ini_get()`에서 읽는다), 운영 서버 php 설정 변경이 필요하다는 점을 알린다. 서버에서 직접 명령을 실행할 수 없으므로 `aiw-ops` 블록으로 등록된 운영 작업명을 요청하거나 관리자에게 설정 변경을 요청해야 한다. 바꿔야 할 값은 `upload_max_filesize`와 `post_max_size`(여유를 두고 더 크게), 웹서버가 nginx면 `client_max_body_size`도 함께다.

답변을 확인하기 전에 코드를 추가로 손댈 필요는 없다. 상태 확인용 명령: `cd /e/xampp/htdocs/leefriends && git status --short && php artisan test --filter=HqRecipeVideoTest`
